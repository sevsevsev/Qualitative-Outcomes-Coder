# Batch 1 (Y2, Y3, Y4): taxonomy and methods review (2026-10-16)

Reviewer: taxonomy, independent. I read the findings, reconciliation, verification table,
STANDARDS S1-S4, DEVIATIONS, CF-016, research-basis.md, the Y2-Y4 data, the registry, design gold
and real-run counts (unique texts, LM/NLM). I did not read held-out gold, and I use no held-out IDs
(R-00). Anything that is not in the verification table is marked "lead". S = SUPPORTED, P = PARTIAL.

## 1. Overall judgement

The Part -> domain -> category -> code hierarchy holds for all three domains. The quality of the
justification differs:

- **Y4** is a model domain. Its categories are CASEL's five competencies, unrenamed, and the anchor
  is current and correctly attributed. Its weak spots are placement (Y4.5, Y4.9 and Y4.12 take
  components from another competency) and FD evidence (section 4).
- **Y3** groups codes by relationship partner. No single anchor uses that axis, but it converges
  with Developmental Assets "Support" and CDC's factors, and statements name the partner. It is
  defensible, but research-basis.md should call the category level codebook-defined with
  convergent support, as the Y1 pilot did.
- **Y2** has no anchor: four frameworks, one or two codes each. Category B puts two unrelated
  constructs together, and a domain named "Engagement" has no engagement code. Only codes are
  assigned, so neither problem needs restructuring. Both should be stated in research-basis.md.

Recurring method problems:

- **Setting features cited as youth outcomes.** NRC/IOM "opportunities to belong" (y3-03) and
  statutory agency duties (y3-09, y3-10) describe what programs provide, which is a Part A
  construct. The verifiers matched wording. Fit to a Part Y code is partial by construction.
- **Imports into an anchored domain.** EASEL "attention control" (a Cognitive-domain skill) into
  CASEL Self-Management, and CCSS ELA into Relationship Skills. These are acceptable only as an
  instance of a CASEL component, never as a new element. That is the Y4.12/NHES precedent.

## 4. One test for merged-components (missed)

S1.6 allows merged-components when "coders can't tell two framework components apart". Several FD
entries argue sparsity or ease of use instead:

- FD-P16: "never confused".
- FD-P04: "no gold rows".
- FD-P05 and FD-P08: "almost no gold rows".
- FD-P06: "few gold rows".
- research-basis.md's Y4 note: "or that had almost no gold rows".

y2 challenged only FD-P16. None of these entries is hidden drift, because each code names only
framework components, and CASEL's bullets are examples within a competency. Escalating any of them
to codebook-defined would misstate the case. Severin should decide once, for every entry: either
"statements rarely separate them" is an acceptable merged-components test (a STANDARDS wording
change), or these are recorded as plain framework coverage. Do not change FD-P16 alone.
